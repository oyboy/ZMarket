# ZMarket

Маркетплейс на микросервисной архитектуре: каталог товаров с категориями и
атрибутами, корзина, заказы с резервированием на складе, отзывы с асинхронным
пересчётом рейтингов, личный кабинет продавца со статистикой продаж.

Проект написан как полигон для изучения таких вещей как: transactional outbox,
CDC через Debezium, CQRS, сага с компенсациями, идемпотентная обработка событий,
двухуровневое кеширование, отказоустойчивость на Resilience4j и для тестирования всего этого.

**Стек:** Java 21 · Spring Boot 3.5 · Spring Cloud · Kafka · Debezium ·
PostgreSQL · Redis · MongoDB · MinIO · Keycloak · Prometheus · Grafana ·
React 19 · Docker Compose

## Безопасность

Аутентификация через **Keycloak** по OAuth2/OIDC.

- JWT проверяется и на шлюзе, и внутри каждого сервиса;
- роли берутся из `realm_access.roles` и преобразуются в authorities
  (`USER`, `SELLER`, `ADMIN`);
- права на операции навешаны на методы: `@PreAuthorize("@productService.isOwner(#uuid)")`,
  `hasAuthority('SELLER')`;
- между сервисами токен пробрасывается Feign-интерцептором;

### Тестовая инфраструктура

`AbstractIntegrationTest` поднимает **PostgreSQL 16 и Redis 7 в Testcontainers**
и прокидывает их адреса через `@DynamicPropertySource`. Flyway применяет те же миграции, что и на дев-окружении

`DatabaseCleanerExtension` очищает таблицы **перед** каждым тестом.

`JwtDecoder` подменён моком, а `TestTokens` выдаёт строковые токены с нужными
ролями и идентификаторами.

Внешние сервисы в `application-test.yml` направлены на заведомо недоступный порт.

### Юнит-тесты

**`ProductServiceTest`** — бизнес-логика в изоляции, на Mockito.
Проверяются: чтение существующего и отсутствующего товара, создание товара
с постановкой остатка на склад и отсутствие обращения к складу при нулевом
остатке, отклонение отрицательной цены и пустого названия, нормализация параметров
страницы с ограничением размера сверху, обновление полей, определение владельца
товара.

**`ReviewServiceTest`** — логика отзывов. Проверка,
что событие в outbox публикуется ровно тогда, когда должно: при создании
отзыва — `CREATED`, при изменении — `UPDATED`, а при повторном сохранении
идентичных данных не публикуется вовсе. Отдельно проверяется запрет оставлять
отзыв на собственный товар, запрет удаления чужого отзыва и отсутствие эффекта
при удалении уже удалённого.

### Интеграционные тесты репозитория

**`ProductRepositoryIT`** 
- Повторное сохранение того же идентификатора не создаёт дубль (`ON CONFLICT DO NOTHING`);
- обновление карточки товара не трогает остаток — им владеет warehouse-service;
- поиск по пустому списку идентификаторов не уходит в базу;
- подсчёт с фильтром по категории;
- выборка товаров продавца;
- рекомендации: исключение текущего товара и ограничение выдачи.

### API-тесты
**`ProductSmokeTest`**
- база отвечает, все семь таблиц из миграций созданы;
- колонки `products`, которые читает `ProductRowMapper`, существуют;
- главная ручка каталога отвечает 200 и укладывается в секунду;
- закрытая ручка отвечает 401, а не падает;
- `/actuator/health` возвращает `UP`.

**`ProductSanityTest`** — основной путь продавца целиком: создать товар →
прочитать по идентификатору → убедиться, что он появился в каталоге своей
категории → убедиться, что он виден в личном списке → обновить → проверить, что
в базе лежит новое значение.

Отдельная проверка согласованности кеша: после обновления карточка отдаёт новое
значение, а не устаревшее из Caffeine или Redis.

**`ProductApiTest`** — детальная проверка ручек каталога.
Сгруппирована через `@Nested` по областям.

### Асинхронные тесты

**`ReviewFlowAsyncIT`**
Testcontainers для PostgreSQL и Redis плюс `@EmbeddedKafka`.

*Параметризованные проверки*:
`PENDING_PUB` + успех → `PUBLISHED`, `PENDING_DEL` + успех → `DELETED`,
любое ожидание + отказ → `REJECTED`.

*Повторы и нарушенный порядок:*
- дубликат сообщения не обрабатывается второй раз;
- опоздавший отказ не отменяет опубликованный отзыв;
- опоздавший успех не воскрешает отклонённый отзыв;
- результат, адресованный другому ожиданию (`PENDING_DEL` для отзыва
  в `PENDING_PUB`), игнорируется.

*Некорректные сообщения:*
- битое сообщение и пустая строка не останавливают обработку следующих;
- результат для несуществующего отзыва не роняет обработчик.

*Сторож зависших отзывов:*
- переотправляет событие для зависшего отзыва, при этом eventId` сохраняется;
- зависший отзыв, для которого события в outbox нет вовсе, отклоняется, а не
  остаётся в ожидании навсегда.

### UI-тесты

**`CatalogUiTest`** — Selenium, с применением паттерна Page Object плюс отдельный слой шагов для отчёта Allure.

Проверяется:
- каталог открывается и показывает непустой список;
- переход на следующую страницу реально меняет набор товаров, а не только
  подсвечивает номер;
- возврат назад показывает ровно то же содержимое, что было;
- на первой странице кнопка «Назад» неактивна;
- обход всех страниц не показывает один товар дважды — склейка страниц на
  стороне браузера;
- поиск без результатов показывает объяснение, а не белый экран;

## Известные ограничения

Проект учебный, и часть решений сознательно упрощена.

- **Платёжный сервис не реализован** — оплата эмулируется контроллером внутри
  order-service, публикующим события успеха или отказа.
- **Секреты в Vault вынесены частично** — туда перенесены учётные данные Keycloak,
  пароли баз данных пока в конфигурации.
- **Отсутсвует CI/CD-пайплайн** — автоматизировано лишь поднятие инфрастуктуры в docker-контейнерах и заскриптована работа с Vault.
